# codex-cli 0.160.0: the record surface beside 0.153.4

Status: read on 2026-10-23 against codex-cli **0.160.0** and, for comparison, **0.153.4**, with **no
paid run, no login and no credential**. It is the evidence for adding 0.160.0 to the Codex
adapter's pin beside 0.153.4. It repeats `2026-10-21-codex-0.153.4-record-surface.md` on the newer
binary and runs both binaries through the same build of the native fixture. On a8's rule the rows
name the binary they were read from, and neither release inherits the other's.

Each row carries one of four labels:

| label | means |
|---|---|
| **observed** | a credential-free run of the named binary in this work shows it |
| **binary** | read from the binary's strings, `--help` or `features list`, not driven |
| **source** | read from the `openai/codex` tree at `rust-v0.160.0` (and `rust-v0.153.4` where compared), not driven |
| **unverified** | none of these; stated so that nobody reads silence as a check |

## What the record carries, and where

Record order of a native 0.160.0 session, the same in all twelve rollouts of the lane (six read
directly from `CODEX_HOME`, six retained by the driver) and the same as 0.153.4's twelve:

| line | record | carries |
|---|---|---|
| 1 | `session_meta` | 0.153.4's keys and **`runtime_workspace_roots`** |
| 2 | `event_msg` `task_started` | the turn id |
| 3–4 | `response_item` `message`, roles `developer` and `user` | the vendor's context blocks |
| 5 | `world_state` | `full`, `state`; `state` has 0.153.4's keys **without `personality` and `orchestrator_skills`** |
| 6 | `turn_context` | 0.153.4's keys and **`disabled_plugin_ids`** (`[]` in every rollout); `personality` is there |
| 7… | the turn | messages, calls, outputs, `token_count`, `task_complete` |

`turn_context` has two key sets on both binaries: nine rollouts per lane carry
`file_system_sandbox_policy` and three do not. The union of record types is the same on both. The
`item_completed` items match: `CommandExecution` `fixture-call-1` completed with exit 0 and failed
with exit 7, `FileChange` `fixture-patch-1` completed with exit `null`. **observed.**

| floor field | 0.160.0 | label |
|---|---|---|
| output style (H1b) | `turn_context.personality`, one record after `session_meta` and before the first call, `"pragmatic"` in all twelve | observed |
| plugin list (H1a) | none of `session_meta`, `turn_context` or `world_state` carries one; `disabled_plugin_ids` names plugins switched off, not the ones loaded | observed |
| credential source (H4) | none of them says which credential the session used | observed |
| MCP server list (H5) | none of them carries one | observed |
| harness version (H9), cwd (H7) | `session_meta.cli_version`, `session_meta.cwd` | observed |

The reader maps none of the new fields and none it maps moved, so the same reader serves both
binaries. The 0.160.0 source adds a rollout record, `RolloutItem::RetainedContext`
(`core/src/session/retained_context.rs:136`, `:211`), and a response item serialised as
`configuration_update` (`protocol/src/models.rs:1238`). Neither appeared in the 24 rollouts
(**observed**). If either is written, the reader keeps it as `opaque` through its unknown-type arms
(`crates/metaharness-codex/src/rollout.rs:227`, `:466`, `:472`). That is the protocol's rule, not a
new mapping (**source**, this repository).

## `personality`

The key's meaning changed between the two releases.

| fact | 0.153.4 | 0.160.0 | label |
|---|---|---|---|
| recorded with no key anywhere | `pragmatic` | **absent** | observed |
| recorded for an explicit `pragmatic`, `friendly`, `none` | as written | as written | observed |
| the `personality` feature | `stable`, `true` | **`removed`, `false`** | binary |
| catalog personality selection | the template's variables | removed: the field is *"retained to decode catalogs produced before personality selection was removed"* (`protocol/src/openai_models.rs:542`) | source |
| what changes the instructions | the catalog entry: under `gpt-5.2-codex` no template text, under `gpt-5.5` the pragmatic template | only `none`, which strips the `# Personality` section (`models-manager/src/model_info.rs:50-56`) | source, and observed below |
| requests in the fixture lane (17 each, `gpt-5.5`, launch key `pragmatic`) | 17 carry "deeply pragmatic" and a `# Personality` header | 0 carry "deeply pragmatic"; 17 carry a `# Personality` header | observed |

Captured requests on 0.160.0 (`gpt-5.5`, one `codex exec` each against a listener on loopback):
no key, `pragmatic` and `friendly` each carry one `# Personality` section and no pragmatic template
text, and their instructions are byte-identical (SHA-256 prefix `cbc4653561fbe2af`). `none` carries
no section (`4d53d254eb76b4ff`). **observed.** The same capture on 0.153.4 came back empty and was
not retried, so the 0.153.4 column above rests on the fixture lane's 17 requests and on the
2026-10-21 page.

So on 0.160.0 the record still says what the launch wrote, and H1b still compares that value with
the launch's `pragmatic`. What the model is told is the same for `pragmatic`, `friendly` and no key.
The 2026-10-21 page's warning holds more strongly: the recorded value is not proof of what the
model was told.

## Command line

`codex exec --help` on 0.160.0 lists the four arguments the launch already refuses and a fifth,
`--worktree`, *"Run the session in a new managed Git worktree"* (**binary**). The launch never
writes it; `guard_arguments` now refuses it beside the other four, because a session moved into a
worktree the launch did not create runs outside the scratch cwd the floor attests. The top-level
`--no-daemon` is a TUI flag, and `mcp-server` is gone from the top-level help (**binary**). Neither
is on the path the launch builds.

## Reproduction

The personality cases, the captures, the feature lists and the help diffs are shell scripts over
the commands above. They are kept with the run's private evidence and not committed; each needs only
the binary, `unshare`, `ncat` and a scratch directory. One native lane per binary:

```console
cargo build --locked --bin metaharness
cargo test --locked -p metaharness-codex --test native_fixture --no-run
unshare -rn sh -c 'ip link set lo up && \
  METAHARNESS_NATIVE_CODEX=<the binary under test> \
  METAHARNESS_NATIVE_CODEX_OFF_PIN=<a codex off the pin> \
  METAHARNESS_NATIVE_DRIVER=$PWD/target/debug/metaharness \
  METAHARNESS_NATIVE_EVIDENCE=<private directory> \
  target/debug/deps/native_fixture-<hash> --ignored --test-threads=1'
```

No transcript is committed. The fixture's responses are synthetic inputs; the vendor records,
process exits and refusals are native observations. No paid model was called.
