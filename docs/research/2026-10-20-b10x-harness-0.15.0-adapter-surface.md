## The served replies that moved

At 0.15.0 the file operations `metaharness-tools` serves run on the `tools` crates through
harness's adapter (`crates/harness-catalogue/src/local.rs`: `file_read`, `dir_list`, `find` on
`b10x-tool-fs`, `file_write`, `file_edit` on `b10x-tool-code-editor`; `search` and `run` stay
local). The catalogue itself — names, descriptions, argument schemas — is unchanged:
`crates/harness-catalogue/src/catalogue.rs` at `dd5c2a66` differs from
`crates/harness-tools/src/catalogue.rs` at `798325f0` only in the toolchain type's path. None of
the moves below crosses `metaharness.event/1`: the b10x adapter writes `content: null` on every
`tool.result`, so they reach a model through `metaharness mcp-serve` and through the loop's own
replies, never a reader of this wire.

Harness's `CHANGELOG.md` `[0.15.0]` names two model-facing reply changes, `dir_list` of a
non-regular entry and a capped `find`, and says of the capped `find` that **`paths` and
`truncated` are unchanged**. Observation 3 found eleven more, and found `truncated` moving too.
Every row is observed on both releases with the same call on the same seeded workspace.

| entry and call | 0.13.3 (`798325f0`) | 0.15.0 (`dd5c2a66`) |
|---|---|---|
| `dir_list` with a FIFO (any non-regular entry) in the listing | `{"bytes": 0, "kind": "file", "name": "pipe"}` | `{"bytes": null, "kind": "other", "name": "pipe"}` |
| `find` capped by `max_results`, the cap reached in one directory and a directory past the depth bound reached afterwards (`capdeep/x/{a,b}.txt`, `capdeep/y/` 14 deep; `{"glob": "*.txt", "path": "capdeep", "max_results": 1}`) | `depth_bound_reached: true`, `truncated: true` | `depth_bound_reached: false`, `truncated: true` |
| `find` capped by `max_results`, only non-matching files after the cap (`cap1/a.txt`, `cap1/b.md`; `{"glob": "*.txt", "path": "cap1", "max_results": 1}`) | `truncated: true` | `truncated: false` |
| `find` with an empty `glob` | refused: *`glob` is required and must not be empty: a find has to name what it is looking for. …* | refused: *… a glob has to name what it is looking for. …* |
| `file_read` with `limit: 0` | an empty window: `{"text": "", "lines": {"from": 1, "to": 0, "total": 1}, "truncated": true, "truncated_lines": [], …}` | refused: *`limit` is how many lines to read and 0 names none. `plain.txt` was not read.* |
| `file_read` whose `max_bytes` equals a last line with no trailing newline (`noeol.txt` = `abc`, `max_bytes: 3`) | the line cut: `"text": "     1\tab\n"`, `truncated: true`, `truncated_lines: [1]` | the whole line: `"text": "     1\tabc\n"`, `truncated: false`, `truncated_lines: []` |
| `file_write` onto a directory (`sub`), and with an empty `path` | refused: *`sub`: Is a directory (os error 21)* | refused: *`sub` is not a regular file* |
| `file_write` to a new name spelled with a trailing `/` (`new2.txt/`) | **written**: `{"path": "new2.txt", "bytes": 1}`, `new2.txt` created | **refused**: *`new2.txt/` is not a regular file*, nothing created |
| `file_edit` whose `old` overlaps itself (`aa` in `aaa`) | **applied**: `{"path": "overlap.txt", "bytes": 2}`, the file became `ba` | **refused**: *that text appears 2 times in `overlap.txt`; include enough surrounding text to name one place (edit 0)*, the file stays `aaa` |
| `file_edit` with an empty `old` | refused: *`old` must not be empty: an edit has to name where it lands* | the same, followed by *(edit 0)* |
| `file_edit` whose `old` matches nothing | refused: *that text appears nowhere in `plain.txt`* | the same, followed by *(edit 0)* |
| `file_edit` whose `old` matches twice (`x` in `x\nx\n`) | refused: *that text appears 2 times in `twice.txt`; include enough surrounding text to name one place* | the same, followed by *(edit 0)* |
| `file_edit` of a file that is not UTF-8 | refused: *`bin.dat`: stream did not contain valid UTF-8* | refused: *`bin.dat` is not UTF-8 text; an edit needs text to find `old` in* |
| `file_edit` of a directory (`sub`) | refused: *`sub`: Is a directory (os error 21)* | refused: *`sub` is not a regular file* |

What moved the two `find` flags: 0.13.3's walk (`crates/harness-tools/src/local.rs`, `walk`)
stopped a directory at the first *file* it visited past the cap and set `truncated` there,
whether or not that file matched, then carried on into the parent's later directories, where it
could still reach the depth bound; `b10x-tool-fs` 0.2.0 stops the whole walk on the first match
past the cap and sets `truncated` only then (`b10x-tool-fs` `src/lib.rs:500-511`, whose comment says *harness 0.13.3 tested it on every visit*). The `file_read` byte-ceiling row is the harness
`[0.15.0]` *Fixed* entry seen from the local provider: that entry names the confined reader, and
0.13.3's local reader charged the separator the same way. The `file_edit` rows are
`b10x-tool-code-editor`'s: it counts `old` overlapping and numbers its refusals by edit.

The other 53 calls answered identically on both releases, reply and workspace, among them: every `search` call;
`file_read` of a plain, empty, CRLF, binary or linked file, through a file, with `offset` 0 or
past the end, and with a short or zero `max_bytes`; `dir_list` of a file, a missing path or a
link; `find` capped with a second match, `max_results: 0`, an invalid glob, under a file or a
missing directory, through a directory link; `file_write` onto a link inside the workspace,
onto a dangling link, below a missing directory or a file, and climbing out of a missing
directory; `file_edit` of a missing file, through links inside the workspace, and a no-op edit.
This bounds the list by those 70 calls, not by every input a model can send.

The adversary's second probe (pass 2, ten more calls on a workspace holding `plain.txt`, `sub/` and
`link-in` → `plain.txt`) found ten more moves outside those 70:

| entry and call | 0.13.3 (`798325f0`) | 0.15.0 (`dd5c2a66`) |
|---|---|---|
| `file_read`, `dir_list`, `find`, `file_edit` of a **missing** path outside the workspace (`../outside-missing.txt`, `/nonexistent-adv2/x.txt`) | refused: *`…`: No such file or directory (os error 2)*, which told a model whether a path outside its workspace exists | refused: *`…` resolves outside the workspace and was refused*, the same text as for an existing outside path |
| `file_read` of an outside path with `offset: 0` | refused for the window: *`offset` is the first line to read …* | refused: *… resolves outside the workspace and was refused* |
| `file_edit` of `plain.txt/` (a file spelled with a trailing `/`) | refused: *Not a directory (os error 20)* | **applied** to `plain.txt` |
| `file_edit` of `link-in/` (a link to a file inside the workspace, trailing `/`) | refused: *Not a directory (os error 20)* | **applied** to `plain.txt`, through the link |
| `file_write` to `link-in/` | refused: *`link-in/` is a symlink, and this workspace writes files rather than through links. Name the file itself.* | **written** to `plain.txt`, through the link |
| `file_write` to `sub/.` | refused: *`sub/.`: Is a directory (os error 21)* | refused: *`sub/.` is not a regular file* |

The first two rows close a leak: 0.13.3 answered whether a path outside the workspace exists.
The trailing-`/` rows open a gap inside the workspace: `file_write` onto `link-in` without the
`/` is still refused as a write through a link (the 70-call probe), but with the `/` it writes
through it. Every target stays inside the workspace (the adversary's containment cases, a link
to a file or a directory outside, a dangling link and trailing `/` or `/.`, all refuse). The
trailing-`/` behaviour belongs to `b10x-tool-code-editor` 0.2.0 and is reported to the tools
owner; metaharness asserts on none of these replies.

## Unverified on 0.15.0, and labelled so

- **Confined process writes.** Both `actual_b10x_process_writes_are_contained_or_explicitly_withheld`
  cases passed on the `withheld-unverified` branch: the record withheld `run` with the reason
  *`exec.argv-only` must be true and this machine says nothing*, no tool was requested and no
  marker file appeared. The delegated root `user@1000.service` offers `cpu memory pids` and no
  `io` controller. The Rust probe's write assertions did not execute; this is no containment claim.
- **The four enforcement excerpts** (`fixtures/enforcement/`) are still 0.9.1 captures. The record
  code they exercise is unchanged since 0.13.3 (source row above); they were not re-recorded.
- **MCP element shape.** `started.mcp` was `[]` in every run here, and `mcp_servers` stays the
  hardcoded `[]`. Harness's own `end_to_end.rs` asserts `mcp[0].connection` and
  `mcp[0].protocol_version` (source only).
- **`cache_creation_input_tokens`** was absent on every `usage` line, because the Responses
  emulator reports no cache-write counter; the 0.14.0 Messages-wire rule (usage unknown unless all
  three counters are present) was not exercised.
- **The llm-based wire.** No `anthropic-messages` run, no subscription or OAuth credential, no
  `credential-renewed` record, no hosted provider, no rate card or `cost` record, no compaction,
  delegation, hooks, skills or memories. 0.14.0's *a turn held to `answer` that ends in prose exits
  1, not 2* was not exercised.
- **Record kinds the adapter carries as `opaque`** — `credential-renewed`, `context-changed`,
  `inventory-changed`, `turn-retried`, `compacted`, `reasoning-delta`, `answered`, the three
  delegate kinds — appeared in none of these runs.
- **The AEP eval arms** (`driven`, `native`) were not run.
