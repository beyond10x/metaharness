login and no credential**. It is the evidence behind design amendment a34
(`story:codex-strict-record-rows`, decision D1 = B): H1b decided from the record, H1a, H4 and H5 left

## What the record carries, and where

Record order of a native 0.153.4 session, the same in all twelve rollouts of the two lanes (six before this change, six after):

| line | record | carries |
|---|---|---|
| 1 | `session_meta` | `base_instructions`, `cli_version`, `context_window`, `cwd`, `history_mode` (`paginated`), `id`, `model_provider`, `originator`, `session_id`, `source`, `thread_source`, `timestamp` |
| 2 | `event_msg` `task_started` | the turn id |
| 3–4 | `response_item` `message`, roles `developer` and `user` | the vendor's context blocks |
| 5 | `world_state` | `agents_md`, `apps_instructions` (`false` here), `collaboration_mode`, `environments`, `host_skills` (the `.system` skills), … |
| 6 | `turn_context` | `personality`, `model`, `approval_policy`, `sandbox_policy`, `permission_profile`, `collaboration_mode`, `cwd`, … |
| 7… | the turn | messages, calls, outputs, `token_count`, `task_complete` |

| floor field | 0.153.4 | label |
|---|---|---|
| output style (H1b) | `turn_context.personality`, one record after `session_meta` and before the first call | observed |
| plugin list (H1a) | none of `session_meta`, `turn_context` or `world_state` carries one | observed |
| credential source (H4) | none of them says which credential the session used | observed |
| MCP server list (H5) | none of them carries one | observed |
| harness version (H9), cwd (H7) | `session_meta.cli_version`, `session_meta.cwd` | observed |

In two driven sessions with a hook (the asked denial, before and after this change) the hook's
request reached the run loop **before** the rollout's record of the same call: the hook channel is
read before the rollout tail. In both, the `turn_context` had already been read. That ordering means
a hook can publish while the opening record is still held; the codex seam then releases the opening
record at once, without the personality, so the hook never waits on it (amendment a34). That path is
exercised by unit tests and the adversary's run-loop cases, not by a native run. **observed** (the
ordering), **unverified** (a native run in which a hook arrived during the hold).

## Config layers

The binary names `/etc/codex/config.toml`, `/etc/codex/managed_config.toml`,
`/etc/codex/requirements.toml`, a project's `.codex/config.toml`, and layer sources `system`,
`project`, `mdm`, `session_flags`, `plugin`, `cloud_requirements`, `cloud_managed_config`,
`legacy_managed_config_file`, `legacy_managed_config_mdm` (**binary**). This machine has no
`/etc/codex` (observed).

Which layer decides the recorded personality, each case one `codex exec` against a closed loopback
port (no provider at all; the rollout's `turn_context` is written before the first request), with
`/etc` replaced by a private tmpfs inside the namespace where a case needed `/etc/codex`:

| case | recorded | label |
|---|---|---|
| no key anywhere | `pragmatic` | observed |
| scratch `config.toml` `friendly` | `friendly` | observed |
| scratch `config.toml` `none` | `none` | observed |
| scratch `pragmatic` and `sandbox_mode = "read-only"`, cwd `.codex/config.toml` `friendly`, project not trusted | `pragmatic` | observed |
| the same, with a `[projects."<cwd>"] trust_level = "trusted"` entry in the scratch config | `friendly` | observed |
| the untrusted case under `sandbox_mode = "workspace-write"` — the sandbox every `--cwd` launch writes — with no trust entry | `friendly` | observed here once; the unit's adversary observed the same in six cases |
| scratch `pragmatic`, `/etc/codex/config.toml` `friendly` | `pragmatic` | observed |
| no scratch key, `/etc/codex/config.toml` `friendly` | `friendly` | observed |
| scratch `pragmatic`, `/etc/codex/managed_config.toml` `friendly` | `friendly` | observed |
| scratch `pragmatic`, `/etc/codex/managed_config.toml` `[features] personality = false` | `pragmatic` | observed |
| `/etc/codex/requirements.toml`, cloud requirements, cloud or MDM managed config | not run | unverified |

So the launch's explicit key wins over the system file, and loses to a managed file and to a
project's file — a trusted project's under `read-only`, and under `workspace-write` an untrusted
one's too; the launch writes no trust entry, and trust does not protect a `--cwd` run. Whichever
wins is what `turn_context` records — and
a layer can also change what the model is told without changing what is recorded (the managed
feature-off row). These are observations about the `personality` key; that other keys follow the
same order is **unverified**.

That is why the launch looks for these layers before it attests (a34 decision 5): it checks which
of `/etc/codex/config.toml`, `/etc/codex/managed_config.toml` and `/etc/codex/requirements.toml` —
every machine-level config path in the binary's strings on Linux — exist, and, under `--cwd`, a
project `.codex/config.toml` in the cwd and each directory above it up to the nearest `.git`,
whatever its trust. When any exists, H2 and H1b are attested unavailable naming them and H1b reads
`unk`. On this machine none exists, so H1b reads `ok` and H2 is imposed.

The check covers **file** layers only. The layer sources `cloud_requirements` and
`cloud_managed_config` (**binary**) are not files: no check sees them, and what they set under a
ChatGPT login is **unverified** — no logged-in run was made. The H1b and H2 claims name them as
unchecked rather than claiming that no layer exists.

## Reproduction

The layer cases and the feature list are shell scripts over the commands above, kept with the run's
private evidence and not committed; each needs only the pinned binary, `unshare` and a scratch
directory. The native lane:

```console
cargo build --locked --bin metaharness
cargo test --locked -p metaharness-codex --test native_fixture --no-run
unshare -rn sh -c 'ip link set lo up && \
  METAHARNESS_NATIVE_CODEX=$HOME/.local/bin/codex \
  METAHARNESS_NATIVE_CODEX_OFF_PIN=<an off-pin codex> \
  METAHARNESS_NATIVE_DRIVER=$PWD/target/debug/metaharness \
  METAHARNESS_NATIVE_EVIDENCE=<private directory> \
  target/debug/deps/native_fixture-<hash> --ignored --test-threads=1'
```

No transcript is committed. The fixture's responses are synthetic inputs; the vendor records,
process exits and refusals are native observations. No paid model was called.
