## The 0.15.1 changes the adapter does not read

Harness's `CHANGELOG.md` `[0.15.1]` has one *Added* and one *Fixed* entry. Besides the `started`
record's `cwd`, which this change reads, the release moves:

| change | where | why it does not reach this adapter or the served surface |
|---|---|---|
| llm 0.8.1 accepts `message_start.message.container` (and other documented empty values) on the Messages wire, where 0.8.0 refused the turn | `9d6a434b`; `crates/harness-llm` | the loop's model port; this workspace links no `b10x-llm-*` crate. No `anthropic-messages` run happened here, so the fix is not observed (unverified below) |
| The session transcript's `workspace` names the tools' canonical root (`open_session` takes `root` instead of canonicalizing `--workspace` again) | `crates/harness-cli/src/lib.rs` | the b10x launch passes `--no-session` (`launch.rs`), so no session file is written, and metaharness reads none |
| `LoopConfig::cwd` / `with_cwd`; an approval checkpoint that names a `cwd` resumes only under it, one that names none resumes under any | `crates/harness-loop/src/lib.rs` (`taken_under`) | no checkpoint is written or resumed by a b10x run metaharness launches; the library type is not used here |
| `chat`, `workflow run`, delegates and forked pairs carry the parent's `cwd` | `5dccbd24` | `workflow run` is the AEP eval's native arm, which is not in the gate and was not run; delegate records are carried as opaque by this adapter |
| harness's own metaharness converter writes `session.started.cwd` from the record | `crates/harness-cli/src/metaharness.rs` | harness's converter, not this repository's reader; this adapter's seam now writes the same value |
| the human renderer ignores `cwd` | `crates/harness-cli/src/render.rs` | the adapter runs `--json` only |

The CLI contract (`contracts/cli/b10x-harness/2026-09-18`) is unchanged (harness `[0.15.1]`).
