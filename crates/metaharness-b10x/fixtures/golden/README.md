# Golden b10x sample — recorded loop wire (adapter contract CT-2)

These are the bytes the released `b10x-harness` 0.15.0 binary wrote during one controlled run
against harness's deterministic local OpenAI Responses endpoint. This is `provider_emulated`
evidence, never `vendor_live`: it tests the adapter against the real loop record without claiming
that a live provider was contacted.

## Provenance

| fact | value |
|---|---|
| captured | 2026-10-20 |
| binary | `b10x-harness 0.15.0`, built with `cargo build --release --locked -p b10x-harness-cli` from the released commit `dd5c2a66218a5f2555c4a9fdab6fdfac8515cc6d` (annotated tag `0.15.0`) |
| endpoint | harness's deterministic `crates/harness-cli/tests/fixtures/fake_responses.py` at that commit, `flat-tool` scenario, bound to `127.0.0.1` inside a network namespace whose only interface is `lo` |
| run shape | constructed child environment (`PATH`, `LANG`, `TMPDIR` only; no `HOME`), scratch workspace holding one `README.md`, **no credential flag** (`credential_source: "none"`; the emulator recorded no `authorization` header on either request), `--no-session`, `--json`, one `file_read` call |
| reviewed | no credential, account identifier, machine path or endpoint address occurs in the committed bytes; `profiles: []` proves the capture did not apply an ambient permission profile |
| replaces | the 0.9.1 capture of 2026-08-31 (`b62612091374b205245ce9a5c16b27217279a567`), which used a named synthetic API-key variable |

`loop.jsonl` is the raw `--json` record. `version.txt` is the version banner captured from the
same binary; the loop record has no version field of its own, so CT-3 pairs these two capture
artifacts rather than inventing one. `loop.expected.jsonl` is generated by replaying the raw record
through `B10xSeam` and is compared byte for byte. The 0.15.0 `started` line names no working
directory, so the replay's `cwd` is `null`, and the vector fails a recording whose `started` line
names a `cwd`, as a 0.15.1 one does (design amendment a30).

## Recording it again

The 2026-10-20 capture took these steps, all inside one
`unshare --user --map-root-user --net` namespace after `ip link set lo up`:

1. Build `b10x-harness` at the pinned revision (`HARNESS_REVISION`).
2. Write `README.md` holding the bytes `hello harness\n` into an empty scratch workspace.
3. Start `python3 -I crates/harness-cli/tests/fixtures/fake_responses.py --scenario flat-tool`
   from that harness checkout and read `base_url` from the JSON line it prints.
4. With the environment cleared to `PATH=/usr/bin:/bin`, `LANG=C.UTF-8` and a scratch `TMPDIR`,
   write `b10x-harness --version` to `version.txt`, then run
   `b10x-harness run --base-url <base_url> --model b10x-emulated --no-session --json
   --input "read the readme and tell me what it says" --workspace <scratch>` from the workspace
   and write its stdout to `loop.jsonl`. It exits 0.

Review the bytes for paths, addresses and credentials before committing them, stamp the replay's
version in `vectors.rs` `reader()` to the banner's, and regenerate the expected event stream only
after reviewing a deliberate mapping change:

```console
cargo test -p metaharness-b10x regenerate -- --ignored
```
